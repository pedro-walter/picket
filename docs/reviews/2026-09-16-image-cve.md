# Image-CVE review — 2026-09-16

Scope: `monitoria-soul-spike`, the only agent with open `image-cve`
findings this pass (`registry` and `soul-spike` only have unrelated `apt`
findings, out of scope). 65 open findings total; 62 are `image-cve`, all
on a single image: `docker.souspike.com.br/healthchecks/healthchecks`.

That subject is the custom overlay built two reviews ago
([`2026-09-13-image-cve.md`](./2026-09-13-image-cve.md),
[`custom-docker/healthchecks/healthchecks/Dockerfile`](../../custom-docker/healthchecks/healthchecks/Dockerfile)).
Since then it was actually built, pushed as `:4.4-1`, and the compose file
on `monitoria-soul-spike` was pointed at it — confirmed by pulling the tag
directly (`docker inspect`, created `2026-09-13T10:35:47-03:00`, single
build, never rebuilt since). Picket rescanned the new image and opened 62
fresh findings against it (`first_seen` 2026-09-14, reconfirmed today).

**None of the old suppression rules apply anymore.** They were all written
against `--subject healthchecks/healthchecks` (the upstream repo name);
the running image's subject is now `docker.souspike.com.br/healthchecks/healthchecks`,
a different string the glob doesn't match. Every finding below is
"new" from Picket's point of view even though most of them are exactly the
same unfixable packages flagged last time.

Confirmed by inspecting the running `:4.4-1` image directly (`docker run

`libsqlite3-0`, `gzip`, `libssh2-1t64`, `libssl3t64`, `openssl`,

**perl-base got a new CVE since:** CVE-2026-9538 (perl-Archive-Tar DoS),
no fix published yet — see suppress list below. The 3 criticals the
overlay closed (13221, 42496, 8376) stayed closed.

## setuptools / msgpack — a real finding, but not the one it looks like

`detail` shows `setuptools 70.3.0 -> fixed in 78.1.1` and `msgpack 1.1.2
-> fixed in 1.2.1` (CVE-2025-47273, GHSA-6v7p-g79w-8964) — which looks
like the overlay's `pip install -U setuptools msgpack` step didn't take.
It did: `pip show` inside the running image reports `setuptools 84.0.0`,
`msgpack 1.2.2`, both well past the fixed versions, at
`/usr/local/lib/python3.14/site-packages`.

What trivy is actually flagging is a **second, separate copy**: pip
vendors its own frozen bundle of both packages at
`/usr/local/lib/python3.14/site-packages/pip/_vendor/`, pinned by
`pip/_vendor/vendor.txt` to exactly `setuptools==70.3.0` /
`msgpack==1.1.2` — independent of whatever's pip-installed at the top
level. `pip --version` inside the image is already `26.2.1`, PyPI's
current latest, so there's no newer pip to bump to that would carry an
updated vendor bundle — this can't be fixed by anything in our control
until pip itself re-vendors these.

Same shape as the `gosu`/stdlib case from the first review: pip is a
build-time tool this container's `uwsgi` entrypoint never invokes at
runtime, so the vendored copies sit dead. Suppress, not rebuild.

The two mariadb criticals (CVE-2026-44172 SQL injection via big5 charset
handling, CVE-2026-49261 arbitrary code execution via `wsrep_notify_cmd`)
both need attacker control of the MariaDB server itself or filesystem
access this container doesn't expose over the network — same caveat as
last review, worth a second look before signing off but not blocking a
suppression. The 4 new mariadb high-severity CVEs share the same "no fix
yet" status and container-doesn't-expose-this-surface logic.

```sh
cd cli/picketctl
EXP=$(date -u -d '+90 days' +%Y-%m-%dT%H:%M:%SZ)
SUBJECT='docker.souspike.com.br/healthchecks/healthchecks'

for pkg in libncursesw6 libtinfo6 ncurses-base ncurses-bin \
           libsystemd0 libudev1 libmariadb3 mariadb-common libacl1 \
           bsdutils libblkid1 liblastlog2-2 libmount1 libsmartcols1 \
           libuuid1 login mount util-linux libcurl4t64 perl-base; do
  ./picketctl rules add --kind image-cve --subject "$SUBJECT" \
    --identifier "*|$pkg" --cve '*' \
    --reason "No Debian trixie-security fix published yet as of 2026-09-16 (docker.souspike.com.br/healthchecks/healthchecks:4.4-1, built from frozen healthchecks/healthchecks:v4.4). Re-superseded from the old healthchecks/healthchecks-subject rules, which stopped matching once the compose file moved to the custom overlay's own subject. libmariadb3/mariadb-common's CVE-2026-44172/49261 additionally require attacker control of the MariaDB server or filesystem this container doesn't expose; the newer 44168/44171/48163/48165 share that same non-exposure." \
    --expires "$EXP"
done

./picketctl rules add --kind image-cve --subject "$SUBJECT" \
  --identifier '*|setuptools' --cve 'CVE-2025-47273' \
  --reason "Not the top-level pip-installed setuptools (that's already 84.0.0, well past the 78.1.1 fix, via this overlay's pip install -U step) - this is pip's own internally-vendored copy at pip/_vendor/, pinned to 70.3.0 by pip 26.2.1's vendor.txt. pip 26.2.1 is already PyPI's latest, so there's no newer pip to bump to. pip is a build-time tool never invoked by this container's uwsgi runtime entrypoint, so the vendored copy is dead code, same shape as the postgres gosu/stdlib suppression from the first review." \
  --expires "$EXP"
./picketctl rules add --kind image-cve --subject "$SUBJECT" \
  --identifier '*|msgpack' --cve 'GHSA-6v7p-g79w-8964' \
  --reason "Same as the setuptools rule above - pip's vendored msgpack copy (pinned 1.1.2 by pip 26.2.1's vendor.txt), not the top-level pip-installed msgpack this overlay already upgraded to 1.2.2. No newer pip available; pip never runs at container runtime." \
  --expires "$EXP"
```

One hit a `picketctl` matching quirk worth flagging: `--cve
'GHSA-6v7p-g79w-8964'` (the exact msgpack advisory id, non-`CVE-`-prefixed)
did not suppress its finding even though the rule's `cve_glob` matched the
finding's stored `cve` field byte-for-byte — the same exact-match pattern
worked fine for `CVE-2025-47273` on the setuptools rule right next to it.
Re-added the msgpack rule with `--cve '*'` instead, which suppressed it
immediately, and deleted the dead exact-GHSA-id rule (id
`798cc281-ea76-4288-bb8a-2e245816b5d0`) so it doesn't sit in `rules list`
looking like it's doing something. Worth a look in `picketctl`'s glob
matcher if a non-`CVE-`-prefixed identifier (GHSA, GO, etc.) shows up
again — this may not be an isolated case.
