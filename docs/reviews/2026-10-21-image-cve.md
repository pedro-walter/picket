**Correction to last week's note.** The 2026-10-19 report said the .NET runtime findings were "a deps.json entry, not
necessarily the runtime radarr runs on". That is wrong. `/app/radarr/bin/Radarr.runtimeconfig.json` in the current
image lists `includedFrameworks` Microsoft.NETCore.App and Microsoft.AspNetCore.App **8.0.27**, and the image ships
`libcoreclr.so`/`System.Private.CoreLib.dll` with no system dotnet. Radarr is a self-contained build, so it really runs
on 8.0.27. The newest Radarr release is v6.4.4.10685 (2026-09-16), which predates .NET 8.0.32. A re-pull does not help:
the current registry build has the same 22.

No overlay: the runtime is bundled into Radarr's publish output, so apk can't upgrade it. No suppression proposed: two
are critical, a patched runtime exists and only Radarr needs to ship it, so these should stay visible. Watch
https://github.com/Radarr/Radarr/releases for a build on 8.0.32 or newer.

## lscr.io/linuxserver/jellyfin:latest (seedbox) — 5 findings

The tag is rolling. The host runs `sha256:799509f8ef3b`. Registry `latest` = `12.2ubu2604-ls55` (`sha256:38f6ad3bcd48`,
pushed 2026-10-19).

| CVE | package | sev | fix published | action | why |
|---|---|---|---|---|---|
| CVE-2026-92392 | curl 8.18.0-1ubuntu2.7 | high | yes (8.18.0-1ubuntu2.8) | **custom rebuild** | `-ls55` still ships 2.7; `apt-get update` in it sees 2.8 as candidate |
| CVE-2026-92392 | libcurl4t64 8.18.0-1ubuntu2.7 | high | yes (8.18.0-1ubuntu2.8) | **custom rebuild** | same |
| CVE-2026-78667, 78669, 97031 | stdlib (`usr/bin/pebble`) | high | Go 1.26.9/1.27.2, not in any image | suppress (`inherit all`) | pebble is never started, see below |

**Custom rebuild — pushed:** `custom-docker/linuxserver/jellyfin/Dockerfile` was built and pushed as
`docker.souspike.com.br/linuxserver/jellyfin:12.2ubu2604-ls55-1` (digest `sha256:69c87568a891…`). Verified in the
built image: `dpkg-query` shows curl and libcurl4t64 at `8.18.0-1ubuntu2.8`, and a local trivy scan of it shows only the
pebble stdlib findings. The base apt sources are the live `resolute` suites, so the Dockerfile needs no snapshot
override. The base has no `USER`: s6-overlay `/init` runs as root and drops to `abc` itself, so the overlay sets none.

This is a **stopgap**. It also freezes jellyfin at `-ls55` instead of following `latest`. linuxserver rebuilds weekly,
so drop the overlay as soon as a newer `latest` carries curl 2.8. To use it, point the jellyfin service in the seedbox
compose file at `image: docker.souspike.com.br/linuxserver/jellyfin:12.2ubu2604-ls55-1` and recreate it. Declare the
lineage the first time (preview, then add `--apply`):

```sh
picketctl lineage add docker.souspike.com.br/linuxserver/jellyfin lscr.io/linuxserver/jellyfin
```

**pebble (suppress).** `/usr/bin/pebble` is Canonical's service manager, which comes with the Ubuntu base. It is not
dpkg-owned, and nothing in `/etc`, `/init`, `/package` or `/command` references it: the container is supervised by
s6-overlay, and nothing ever runs pebble. So its `net/http`/`crypto/tls` code isn't on any running path. The current
registry build moved it to Go 1.27.1, which is still vulnerable (fixed in 1.27.2), and my local trivy DB already shows
a fourth CVE (CVE-2026-111943, fixed in 1.27.3) that the agent will likely report next. That CVE is included below.
`--inherit all` lets these carry over to the overlay above once the lineage edge exists.

```sh
for c in CVE-2026-78667 CVE-2026-78669 CVE-2026-97031 CVE-2026-111943; do
picketctl rules add --kind image-cve --subject lscr.io/linuxserver/jellyfin --identifier "$c|stdlib" --cve $c \
  --reason "Go stdlib inside usr/bin/pebble (Canonical service manager from the Ubuntu base, not dpkg-owned). Never started: container is supervised by s6-overlay and nothing in /etc, /init, /package or /command references pebble (checked 12.2ubu2604-ls55, 2026-10-21). Re-check if linuxserver changes init." \
  --expires 2027-01-19 --inherit all
done
```
