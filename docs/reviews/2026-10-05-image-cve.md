## Follow-up (same day): vendored-copy check on bazarr, exposure-based triage

Checked against `lscr.io/linuxserver/bazarr:latest` pulled locally (image built 2026-09-26). This is the image
content, not the running seedbox container; it is the same image, but nobody inspected the live container.

**Bazarr vendored copies — confirmed pip's.** `pip 26.2.1` at `/lsiopy/lib/python3.12/site-packages/pip/_vendor/`
has `urllib3` and `msgpack` directories, and its `vendor.txt` pins exactly `urllib3==2.7.0`, `msgpack==1.1.2`,
`setuptools==70.3.0` (the last ships as pip's vendored `pkg_resources`). Bazarr's own top-level setuptools is
84.0.0, past the fix. pip is not run at runtime: `svc-bazarr` never calls it; the only pip use in the container
is the `init-mods-package-install` hook, which does nothing unless `DOCKER_MODS` is set. The 4 `@vendored` rules
are justified; the reason text can cite the above.

**Correction to my table: bazarr's top-level urllib3 2.7.0 is real**, not a pip copy: it is the app's own
bundled `/app/bazarr/bin/libs/urllib3-2.7.0.dist-info`. (Its bundled msgpack is already 1.2.1, fixed.) Only
upstream bazarr can bump that, and it is a DoS/proxy-TLS issue in an HTTP client. Fine to leave given exposure.

**qbittorrent is not fixed by re-pulling.** Latest was built 2026-09-29 and still has `python3 3.14.7-r1` and
`pcre2 10.48-r0`. `/app/qbittorrent-nox` links no pcre2; in that image pcre2 is only pulled in by `grep`. Python
is there for qbittorrent's optional search-engine plugins.

### Triage by exposure

Only qbittorrent is (or will be) reachable from the internet; everything else is LAN-only, so remote-attacker
vulnerabilities there are not worth effort beyond a routine re-pull.
